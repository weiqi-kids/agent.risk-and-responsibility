## 1. 核心資訊

| 項目 | 內容 |
|------|------|
| **網站名稱** | Risk & Responsibility Intelligence |
| **一句話描述** | 開源 AI 情報系統，每週自動追蹤全球風險管理框架、法規與產業標準的變動，結構化呈現責任歸屬的演化趨勢 |
| **核心價值主張** | 整合 NIST、EUR-Lex、CISA、ISO、SANS、CSA 等 7 大權威來源，透過 L1-L4 四層結構化萃取，將分散的法規訊號轉化為可行動的合規情報——免費、開源、每週更新 |

### 定位聲明（Positioning Statement）

針對**需要追蹤跨區域法規與框架變動的資安及合規專業人員**，
Risk & Responsibility Intelligence 是一套**開源自動化情報系統**，
它**每週整合 7 大權威來源、產出 7 份結構化報告**，
不同於人工彙整或付費訂閱服務，我們的**萃取邏輯完全公開透明，且獨創責任變動追蹤分類**。

## 2. 目標受眾

### 主要受眾 (Primary)

| 項目 | 描述 |
|------|------|
| **是誰** | 企業 CISO、資安主管、法遵/合規主管（中大型企業，需同時關注美國、歐盟、國際標準） |
| **目標/需求** | 快速掌握每週法規變動，評估對組織的影響，在合規審查與管理層彙報中展現主動監控能力 |
| **痛點** | (1) 法規來源分散於 NIST、EU、ISO 等，人工追蹤每週耗費 4-8 小時；(2) 難以判斷哪些變動真正影響自身組織；(3) 缺乏結構化的「責任歸屬變化」追蹤機制 |
| **使用場景** | 每週一早晨瀏覽 Executive Summary 掌握全貌，再深入特定 Mode 報告；季度合規審查前回溯歷史變動；向董事會彙報風險態勢前的快速準備 |

### 次要受眾 (Secondary)

| 項目 | 描述 |
|------|------|
| **是誰** | AI/ML 產品團隊（PM、工程師）、採購/供應商管理人員、OT/ICS 安全人員 |
| **目標/需求** | 了解特定領域（AI 治理、供應鏈安全、關鍵基礎設施韌性）的最新法規要求與實作指引 |
| **痛點** | (1) 專業領域法規變化快速但分散；(2) 缺乏將法規要求轉化為技術實作步驟的橋梁；(3) 供應鏈盡職調查缺乏系統性框架追蹤工具 |
| **使用場景** | AI 產品上線前檢視 AI Governance Landscape + Implementation Guide；供應商評估時查閱 Supply Chain Security 報告；基礎設施安全規劃時參考 Critical Infrastructure Resilience 報告 |

### 潛在受眾 (Tertiary) [假設]

| 項目 | 描述 |
|------|------|
| **是誰** | 資安顧問公司、法律事務所、學術研究者 |
| **目標/需求** | 作為二手資料源引用，或建構自有服務的基礎資料集 |
| **使用場景** | 引用結構化萃取資料進行趨勢分析；在顧問報告中參考本站的責任變動分類 |

## 3. 差異化定位

| 項目 | 內容 |
|------|------|
| **與競品的差異** | (1) 完全開源——萃取邏輯、報告產出流程皆可檢視審計；(2) 免費使用——無訂閱費、無分級付費牆；(3) 結構化四層萃取（L1 Rule Signal → L2 Responsibility → L3 Risk Model → L4 Obligation）而非單純轉載 |
| **獨特優勢** | (1) **責任變動追蹤**：獨創 `shift_type` + `affected_roles` 分類，追蹤責任歸屬如何隨法規演化——這在商業競品中未見；(2) **7 來源 × 7 報告**的多維交叉分析；(3) 851+ 份結構化文件組成的知識庫可供語意搜尋 |
| **不做什麼** | 不提供法律建議或合規認證服務；不取代人工專家判斷；不處理機密、付費或非公開資料源；不提供即時警報（週報週期） |

### 競品光譜

| 面向 | Risk & Responsibility Intelligence | 商業法規追蹤服務（如 Thomson Reuters、LexisNexis） | 開源威脅情報（如 MITRE ATT&CK） |
|------|-------------------------------------|---------------------------------------------------|--------------------------------|
| 成本 | 免費 | 年費 $10K-$100K+ | 免費 |
| 來源整合 | 7 大權威來源（框架+法規+威脅+標準） | 廣泛但偏法律 | 偏技術攻擊面 |
| 責任追蹤 | 有（結構化 L2 層） | 無系統化追蹤 | 無 |
| 更新頻率 | 每週/每月 | 即時/每日 | 不定期 |
| 透明度 | 完全開源 | 黑箱 | 開源 |
| 行動指引 | 有（AI Implementation Guide） | 有（付費顧問服務） | 有限 |

## 4. 品牌調性

| 項目 | 描述 |
|------|------|
| **語氣** | 專業、中立、謹慎——明確標註 AI 推論與事實的區別；資訊密集但不冗長；避免行銷語言，以數據和來源說話 |
| **視覺風格** | 簡約、結構化、表格驅動；Just the Docs 主題提供清晰的導航和深色/淺色模式；資訊架構優先於裝飾性設計 |
| **關鍵字** | 風險管理（Risk Management）、責任歸屬（Responsibility Attribution）、合規自動化（Compliance Automation）、開源情報（Open-Source Intelligence）、結構化萃取（Structured Extraction） |
| **品牌個性** | 像一位嚴謹的分析師同事——不浮誇、不煽動，提供你可以直接引用的結構化資料；承認 AI 系統的局限性，強調人機協作 |

### 語氣準則

| 做 | 不做 |
|----|------|
| 標註來源機構和日期 | 使用「震驚」「重磅」等煽動性詞語 |
| 區分「已生效」和「草案階段」 | 將草案描述為已定案 |
| 標註 `[系統推論]` 或 `[REVIEW_NEEDED]` | 省略不確定性標記 |
| 提供具體行動建議（做什麼、什麼時候） | 只描述問題不建議行動 |

## 6. 改版目標

### P0 — 必須達成

| 目標 | 說明 | 預期效果 |
|------|------|----------|
| **改善 Core Web Vitals** | TBT 從 660ms 降至 200ms 以下；確保 LCP、CLS 均通過閾值 | Google 排名因素改善；使用者互動體驗提升 |
| **提升 E-E-A-T 信號** | (1) 加入人工審核者/編輯者資訊；(2) 在 About 頁面呈現團隊背景與方法論；(3) 強化免責聲明的顯眼度 | 降低「純 AI 生成」的可信度風險；提升 Google 對 YMYL 類內容的信任度 |
| **補齊 W12 報告缺口** | AI Governance Landscape 和 AI Implementation Guide 缺少 W12 週報 | 7/7 Mode 皆有完整的每週/每月產出，展現系統穩定性 |

### P1 — 重要但可延後

| 目標 | 說明 | 預期效果 |
|------|------|----------|
| **強化行動指引** | 每個規則變動加入具體行動步驟（who/what/when）和合規時程建議 | 從「知道發生了什麼」提升至「知道該做什麼」，增加實用價值 |
| **改善導航與資訊架構** | (1) 首頁「本週報告」區塊自動更新為最新一期；(2) 增加按日期/主題的交叉導航；(3) 加入搜尋功能 | 降低找到特定報告的時間成本，提升回訪率 |
| **SEO/AEO 結構化標記** | 確保所有報告頁面包含 `layout: report`、`seo:` front matter、FAQ schema、`.key-takeaway` 和 `.key-answer` 標記 | 提升搜尋引擎精選摘要（Featured Snippet）和 SGE 引用機率 |
| **修復 eu_regulations 資料源** | EUR-Lex RSS 目前回傳空檔（自 W09 起），需要替代抓取方案或備援來源 | 恢復歐盟法規的完整涵蓋 |

### P2 — 有最好

| 目標 | 說明 | 預期效果 |
|------|------|----------|
| **視覺化呈現** | 加入趨勢圖（每週變動數量）、責任轉移 Sankey 圖、來源分布圓餅圖 | 降低認知負荷，讓非技術受眾更容易消化資訊 |
| **跨期比較功能** | 提供週報之間的差異比較，標示新增/移除/修改的項目 | 讓回訪用戶快速辨識增量變化 |
| **RSS Feed 完善** | 目前首頁有 RSS 連結但標註為「規劃中」，需實作完整 RSS/Atom feed | 支援自動化訂閱工作流，降低回訪摩擦 |
| **多語言支援** | 英文版報告（目前以繁體中文為主） | 擴大國際受眾覆蓋 |
| **API 存取** | 提供結構化資料的 JSON API 端點 | 讓其他系統整合本站資料 |

## 8. 技術架構評估

### 現有技術棧

| 組件 | 技術 | 評估 |
|------|------|------|
| 靜態網站 | Jekyll + Just the Docs + GitHub Pages | 適合當前規模；部署自動化已完備 |
| 向量搜尋 | Qdrant + text-embedding-3-small | 支撐語意搜尋需求 |
| CI/CD | GitHub Actions（build-index、check-sources、pages） | 3 個 workflow 覆蓋核心自動化需求 |
| 資料格式 | Markdown + YAML front matter + JSONL | 標準化程度高，利於維護 |

### 技術改善機會

| 項目 | 優先級 | 說明 |
|------|--------|------|
| TBT 優化 | P0 | 可能因 Just the Docs 預設 JS 或搜尋索引過大導致；需 Lighthouse 診斷具體瓶頸 |
| 搜尋功能 | P1 | Just the Docs 內建 lunr.js 搜尋，但 851+ 文件的索引可能過大；考慮替換為 Pagefind 或伺服器端搜尋 |
| Structured Data | P1 | 加入 JSON-LD（Article、FAQPage、HowTo）提升搜尋引擎理解度 |
| RSS/Atom Feed | P2 | 利用 jekyll-feed 外掛自動產生 |
